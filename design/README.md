## Provenance boundary

`platos-ui-refactor.provenance.json` deterministically records all **57** files under `platos-ui-refactor/`, their current SHA-256 values, repository-history source evidence, and the repository Apache-2.0 licence declaration. It records repository evidence only and does not assert external ownership.

The design `assets/logo.png` remains an `unknown-origin-brand-asset`: Git establishes its import, but no earlier repository source or external owner is derivable. `assets/platos-icon.svg` is a transformed repository copy and is deliberately **not** claimed byte-identical. The manifest records one known four-file byte-identical logo set and rejects symlinks, outside-root targets, non-regular Git modes, schema drift, and nondeterministic output.

## How to use this

**Reference, not production code.** These are static HTML mockups. The real screens are built in `apps/webapp` against the Platos domain model and the actual API. Take the visual system, layout decisions, component shapes and interaction intent from here — not the markup.

### The design system is the durable part

`styles.css` carries the tokens the rebuild should adopt:

```css
--density: 1;                              /* global density multiplier */
--pad-card: calc(20px * var(--density));
--pad-row:  calc(14px * var(--density));
--gap:      calc(16px * var(--density));
--radius: 10px;  --radius-sm: 6px;  --radius-lg: 14px;
```

Type runs dense by design — 10/11/12/13px dominate, which suits operators reading tables and traces rather than browsing.

**Density is parameterised on purpose.** Lowering `--density` tightens every screen coherently. The mockups ship at `1`; `0.75`–`0.85` is worth trying for the data-heavy screens (tool registry, threads, traces, audit).

### Known limitations of the mockups

- **They render 3–9 rows per list.** The tool registry shows 3 tools; it should scale to ~200. Layout behaviour at real volume is unexplored — virtual scrolling, sticky headers, grouping and column priority are all open questions the mockups don't answer.
- **List screens are div-based, with no `<table>`.** For genuinely tabular data at scale, real tables are usually better: column alignment, sticky headers, sortable columns, keyboard navigation.
- Empty, failure and dense states were requested in the brief but are not comprehensively covered here. The brief (`WIN-154`) lists what each screen needs.

### Vocabulary

The mockups use the ratified nouns from `docs/domain-model.md` — Agent, Thread, Turn, Step, Tool, Entity, Skill, Memory, Artifact, **Job** (not "task"). Keep them consistent when building.
