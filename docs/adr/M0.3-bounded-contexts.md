# ADR M0.3 — Bounded-Context Decomposition & Dependency Direction for Platos V1 (WIN-248)

**Status:** **ACCEPTED (with qualification), 2026-08-28** · **Supersedes:** nothing · **Feeds:** M2.1 (extract domain contracts), M2.2 (BFF Prisma removal)

> **Immutable evidence.** This ADR is accepted and frozen. Do not edit accepted decisions in place — a future architectural change is recorded in a new, superseding ADR that references this one. The decision record is §7.

**Synthesis basis:** Spine = the canonical-store-write-ownership decomposition (score 31/40; top on ownership-clarity 9 and charter-fit 9). Grafted, per judge guidance: (a) from the capability-vertical proposal — the *sole-writer lint extended from the existing `clean-prisma-delegates.test`*, the *identity-isolation import denylist*, and *kernel-hosted decoupling ports* (`SafetyEventSink`, `ErasureTarget`, `DurableRuntime`) to kill fan-in cycles; (b) from the lifecycle-layer proposal — the *kernel-as-true-leaf rule* and the *reader-port dependency-inversion* pattern applied selectively at read-seams. Three latent cracks the judges found in the spine are fixed here: `ToolCall` sole-writer contradiction, the `privacy ↔ everyone` fan-out, and the leaked-Prisma-txn outbox.

## 1. Decision — the bounded contexts

**Cutting rule:** every canonical row has exactly **one** context permitted to write it; every external system (Trigger DB, ClickHouse, MinIO, Redis, provider APIs, channel APIs) is reached only through a Platos-owned port whose adapter is the *sole* holder of that vendor SDK. Where two current modules co-write the same tables they are **one** context (→ `tool-gateway` + `mcp-platform` merge into `tools`); where one module writes tables of three owners it is **split** (→ `monitoring` splits into `cost-monitoring` / `governance` / `observability`).

**Count: 17 domain contexts + 1 infrastructure adapter-context (`durable-runtime`) + 1 shared-kernel package (`platform-kernel`) = 19 packages.** This granularity is deliberate: the spine's 785-capability matrix and the two 7k monoliths do not collapse into 4–5 contexts without re-creating a god-module (the lifecycle-layer alternative's `runtime-core` openly "risks re-congealing into the very agent.service monolith"). Finer than ~17 mostly adds thin packages; the genuinely mergeable pairs are surfaced as founder decisions (§7) rather than pre-decided.

Every other context is a narrow, single-owner slice. The three broadest capabilities the old `monitoring` conflated are deliberately three contexts (13/14/12).

## 2. Dependency-direction ADR

**Onion, per context.** Each of the 17 domain contexts and `durable-runtime` is a package with exactly these layers, and imports point **inward only**:

```
transports (REST / MCP / WS / webhook / channels-ingress / BFF)
  → application (commands / queries / use-cases)      ── define the ports
    → domain (entities, value objects, events)
      ← adapters (Prisma / Redis / ClickHouse / MinIO / providers / channels / Trigger)  implement ports, depend INWARD
```

- `application` may import `domain`. `domain` may import nothing but `platform-kernel`.
- `adapters` and `transports` may import that context's own `application` + `domain` + `platform-kernel` — **never** the reverse; `domain`/`application` must never import `adapters` or `transports`.
- **Cross-context:** a context may import another **only via that other context's published contracts (ports + DTOs + integration events)** — never its `domain`, `application`-internals, or `adapters`. The allowed edge-set is exactly the `domainDeps` DAG in §1.
- **Reader-port inversion (selective graft):** where an upstream owner must *drive* a downstream engine (channel inbound → start a turn; tool "run-agent-as-tool"), the arrow is **never** owner→conversations. It inverts through the kernel `DurableRuntime`/`EventBus` seam (job enqueue or event), keeping `conversations` a sink.

**Banned imports in `domain/**` and `application/**` of every context (the charter purity rule):**

```
@nestjs/*        prisma / @prisma/* / any generated prisma client
ioredis / redis  @clickhouse/*        minio / @aws-sdk/*
@trigger.dev/*   @modelcontextprotocol/*
openai / @anthropic-ai/* / any provider SDK
```

Domain and application see infrastructure **only** as Platos-owned port interfaces from their own `application/ports` or from `platform-kernel`. This is the charter's non-negotiable list, enforced mechanically in §5.

## 3. Cycle-destination table (acceptance criterion)

Every real cycle and wrong-way edge from the M0.1/M0.2 ground truth, with a concrete destination. **All 8 have a landing site; none is hand-waved.**

| Ground-truth edge (files) | Side A lands in | Side B lands in | Inversion mechanism |
|---|---|---|---|
| **agent-runtime ↔ mcp-platform** (1 / 3) | runtime → **conversations** | mcp → **tools** (merged) | Forward: `conversations → tools` via `ToolExecution` port. The 3 reverse imports ("run agent as MCP tool"/subagent) become a **`DurableRuntime` job** (`/internal/subagent-turn`), not a code edge. |
| **agent-runtime ↔ tool-gateway** (5 / 2) | runtime → **conversations** | gateway → **tools** | The 5 forward calls internalize behind `ToolExecution`/`ToolRegistry` ports. The 2 back-edges (`execute-as-agent`, stream callback) become a **durable subagent job hop + a `TurnMessage` event**. No import back into conversations. |
| **agent-runtime ↔ channels** (2 / 2) | runtime → **conversations** | **channels** (own context) | No direct edge either way. Inbound: channels writes `ChannelEventInbox`, **enqueues a turn job via `DurableRuntime`**. Outbound: channels **subscribes to the `OutboundAssistantMessage`/`TurnMessage` event**. The 2 channel controllers physically move into `channels/transport`. |
| **agent-runtime ↔ skills** (3 / 1) | runtime → **conversations** | **skills** (own context) | Forward: `conversations → skills` via read-only `SkillResolver` + `SkillRuntime` ports (3 calls). The 1 back-edge: shared type **hoisted to `platform-kernel`**; any skill-initiated run routed through a **`DurableRuntime` job**. |
| **mcp-platform ↔ tool-gateway** (3 / 2) | **tools** (merged) | **tools** (merged) | **Collapsed** — both are sole co-writers of `Tool`/`ToolHealth`/`EntityMcp*`, so they become ONE context; the 3+2 imports are now intra-context. **Internal direction is enforced one-way:** `mcp-dispatch → tool-registry`, never the reverse (closes the residual-module-cycle crack the judge flagged). `McpToken`/`McpBearerToken` writes relocate to **identity-access**. |
| **auth → tool-gateway** (2 files: `auth.service`→`ToolRegistryService`, `auth.module`→`ToolGatewayModule`) | **identity-access** (leaf) | **tools** | **Physical delete.** Remove the `ToolRegistryService` import from `auth.service.ts` and `ToolGatewayModule` from `auth.module.ts`. Tool↔scope validation moves to execution time **inside tools** (`tools → identity-access` for scopes, one-way). identity-access **never** imports tools — locked by the identity-isolation denylist (§5). |
| **auth → providers** (4 files: `provider-health.service` inside auth) | **identity-access** | **providers** | **Physical move.** `provider-health.service.ts` (+ test) leaves auth for `providers`, beside `PROVIDER_MANIFESTS` + `ScopedEnvService`. identity-access drops the `ProvidersModule` import. Edge vanishes (intra-context). |
| **auth → monitoring** (1 file: `rate-limit.guard`→`SafetyEventService`) | **identity-access** | **governance** | **EventBus inversion via kernel port.** `rate-limit.guard` publishes a `SafetyEvent` domain event through the kernel **`SafetyEventSink`** port; `governance` implements the sink, is sole writer of `SafetyEvent`, wired at the composition root. No identity→governance code edge. |

**Two self-introduced cycles the judges flagged in the source proposals, pre-empted here:**

- **`privacy ↔ everyone` fan-in/out.** Neither "privacy defines a port everyone implements" (fan-in cycle) nor "privacy imports every context" (10-way fan-out). Instead **`ErasureTarget` is a kernel-hosted port**; each context implements it for its own rows; the composition root injects `ErasureTarget[]` into privacy. `privacy` depends on `tenancy + kernel` only.
- **Leaked-Prisma-txn outbox.** No context passes a Prisma txn handle across a port. `platform-kernel` defines `UnitOfWork` + `OutboxWriter`; producers call `OutboxWriter.append(event, uow)` inside their own `UnitOfWork`; the **kernel outbox adapter is the single physical writer** of the `Event` table; `observability` and `eventing` are drain-side consumers. One transactional outbox, multiple drains (§7.8).

### 5.2 Sole-writer lint — extend the existing `clean-prisma-delegates.test`

The repo **already has** `clean-prisma-delegates.test`; extend it with a checked-in ownership map (the §1 SOLE-WRITER column) and assert that mutating delegates for a model appear only under its owner:

```ts
// contexts/_meta/table-ownership.ts  (single source of truth, also feeds dependency-cruiser (d))
export const OWNER: Record<string, Context> = {
  User: 'identity-access', /* … */ Entity: 'tenancy',
  ToolCall: 'tools', ToolCallAudit: 'tools', SafetyEvent: 'governance',
  Thread: 'conversations', Turn: 'conversations', Step: 'conversations',
  Budget: 'cost-monitoring', AdminAudit: 'observability', Event: '<kernel-outbox-adapter>', /* … all rows */
};
const MUTATORS = /\.(create|createMany|update|updateMany|upsert|delete|deleteMany)\b/;
// FAIL if a file under packages/(contexts|adapters)/<X> calls a MUTATOR on prisma.<model>
//      whose OWNER[<model>] !== <X>.  Reads (findMany/findUnique) are exempt.
```

This converts the ownership map and every wrong-way edge from aspiration into a non-regressable gate, independent of context count.

### 5.3 Kernel-content assertion

A tiny AST test over `packages/kernel/src/**`: fail if any file declares a class with a non-empty constructor, imports anything outside `packages/kernel`, or exports a value that is not an interface / type alias / const enum / frozen object / pure function. This is what keeps the shared kernel from becoming a junk drawer while it hosts `DurableRuntime`/`SafetyEventSink`/`ErasureTarget`.

## 6. File-size / complexity budgets

The 7.1k `agent.service.ts` + 7.0k `agent.controller.ts` are the failure these budgets exist to prevent. Enforced by ESLint (fails CI) plus one custom check.

`.eslintrc` (applies to `packages/contexts/**` and `apps/core-api/src/transports/**`):

| Budget | Value | Rule |
|---|---|---|
| Max lines per file | **500** hard error (warn at 400) | `max-lines: [error, {max:500, skipBlankLines:true, skipComments:true}]` |
| Max lines per function/method | **80** | `max-lines-per-function: [error, {max:80, skipComments:true}]` |
| Cyclomatic complexity per function | **15** | `complexity: [error, 15]` |
| Constructor-injected deps per class | **6** (warn), **8** hard | `max-params` on constructors + custom `max-injected-deps` |
| Nesting depth | **4** | `max-depth: [error, 4]` |
| **Routes per controller** | **12** | custom `max-routes-per-controller` (counts `@Get/@Post/@Put/@Patch/@Delete/@MessagePattern` decorators per class) |
| Public methods per application service | **10** (warn) | custom `max-public-methods` |

Two structural corollaries:
- A turn's orchestration in `conversations` must be split into **named sub-use-case files** (prompt-build, tool-loop, structured-output, multimodal, compaction, dispatch), each ≤500 lines — the `max-lines` wall is the package-internal equivalent of the boundary the lifecycle-layer proposal admitted its `runtime-core` lacked.
- `BudgetService` (18 methods) exceeds the 10-public-method budget and must be split (e.g. `BudgetPolicy` / `BudgetLedger` / `BudgetGuard`) when it lands in `cost-monitoring`.

Budgets are advisory-warn during the strangler migration and flip to hard-error per package as each context is extracted, so legacy `apps/agent` files do not block unrelated work but no *new* monolith can form.

## 7. Decision record (ACCEPTED 2026-08-28)

All ten decisions below are **accepted as recommended**, with one qualification:

> **Decision #9 (sync → async on reverse edges) — accepted WITH qualification.** Durable job hops are accepted for the internal reverse flows (subagent / execute-as-agent / MCP-tool-as-agent). **BUT any existing synchronous API must retain its observable result/error semantics through an enqueue-and-wait compatibility façade** — the caller still receives the terminal result or error, not an accepted-and-detached acknowledgement. **No silent conversion to fire-and-forget.** The async default applies to the internal execution mechanism; the external contract remains synchronous where it is synchronous today.

Decisions 1–8 and 10 are accepted exactly as recommended below. The recommendations are retained as rationale.

---

Genuine judgment calls where reasonable architects differ. Each: options → recommendation.

1. **identity-access and tenancy: two contexts or one?** The lifecycle-layer proposal merged them into a single `kernel-identity-tenancy` leaf. **Options:** (a) two contexts, identity-access as the leaf, `tenancy → identity-access`; (b) one merged leaf. **Recommend (a).** Splitting keeps ownership crisp (auth tokens vs. the tenant tree are different change-cadences) and the leaf rule on `identity-access` alone already kills all three wrong-way auth edges — merging buys nothing the isolation lint doesn't already give.

2. **Overall granularity — keep 17 domain contexts or consolidate the thin ones?** Thin candidates: `secrets`, `eventing`, `jobs`. **Options:** keep all; or fold `secrets→providers`, `eventing→cost-monitoring`, `jobs→durable-runtime`. **Recommend keep `secrets` and `jobs` separate** (secrets is the encryption boundary — collapsing it tempts providers to write ciphertext directly; jobs is the Platos-side approval/record seam distinct from the Trigger adapter), **and consider merging `eventing`'s notification routing into `cost-monitoring`** only if notifications stay alert-shaped. Revisit after M2.1 sizing.

3. **Where `BudgetService` lands, and where enforcement runs.** Ownership: `cost-monitoring` (recommended, spine). But `BudgetGuard` pre-spend check is on the **hot turn path** — the lifecycle-layer proposal's version put budget reads top-of-stack and dented latency. **Options:** (a) `conversations` calls `cost-monitoring.BudgetGuard` synchronously (fresh, +1 read/turn); (b) `BudgetGuard` reads a cached cap + async-reconciles spend. **Recommend (b)** — cached guard, exact reconcile off the outbox.

4. **`ToolCall` sole-writer — `tools` or `conversations`?** Source proposals contradicted each other here. **Options:** (a) `tools` writes `ToolCall`+`ToolCallAudit` (executor owns the execution record); `conversations` writes a `Step` that references it. (b) `conversations` owns `ToolCall` as part of the turn transcript. **Recommend (a)** — the executor is the writer; keeps single-writer crisp. Reversible via the ownership map without moving code between contexts other than the repo.

5. **`AgentSkill` binding — `agents` or `skills`?** **Options:** (a) `agents` owns it (loadout is part of the agent version), `agents → skills` one-way; (b) `skills` owns it, `skills → agents`. **Recommend (a)** — treats loadout as authoring, and it is the direction that keeps `skills` a lower, more-reused context. Genuinely flippable; flipping moves one write-owner and one DAG edge.

6. **`Entity` — `tenancy` or `channels`?** The spine placed a channel-`Entity` in channels; the charter capability list groups `entity` under tenancy. **Options:** (a) `Entity` is the tenant-tree leaf in `tenancy`, channels references it by id; (b) channels owns a `ConnectedEntity`. **Recommend (a)** — bindings across many contexts key off Entity; it must be structural, not channel-specific.

7. **Does the `webapp` Remix BFF survive, or get absorbed into `core-api`?** **Options:** (a) BFF survives as a Remix transport; M2.2 removes its 117 direct-Prisma loaders/actions so all data flows through `core-api` query ports; (b) absorb the BFF into `core-api` transports outright. **Recommend (a)** now — smaller blast radius, keeps the single deployable, and the `webapp-no-prisma` lint (§5) enforces the M2.2 migration. Absorption is a later, optional call once the query-port surface is stable.

8. **One transactional outbox or two?** The spine had a separate `ObservabilityOutbox`; this synthesis unifies on the single kernel `OutboxWriter` with multiple drain consumers (`observability` projection, `eventing` notifications). **Options:** (a) one outbox, split the *drain* if volume demands; (b) two physical outboxes from day one. **Recommend (a)** — one write path removes the leaked-txn violation; split reads later if ClickHouse projection volume warrants.

9. **Accept the sync→async behavior change on reverse edges?** The subagent / execute-as-agent / MCP-tool-as-agent paths convert synchronous returns into `DurableRuntime` job hops that **park on a waitpoint** — a real failure-model change, not a mechanical move. **Options:** (a) accept async everywhere (durable, but changes latency + error semantics, needs correlation-id tracing); (b) keep a synchronous in-process fast-path port for latency-critical MCP tool calls, async for the rest. **Recommend (a) as default, (b) only if a measured latency SLO forces it.** This is the one place the migration is behavior-changing and warrants explicit sign-off.

10. **`durable-runtime` owns the entire Trigger DB behind one port.** **Options:** (a) full encapsulation — no domain context touches `internal-packages/database`, everything goes through `DurableRuntime`; (b) leave Trigger tables partially visible for ops queries. **Recommend (a)** — it is what makes "one deployable, Trigger behind a port" true and keeps the SDK containment lint meaningful.

**M2.1 hand-off:** the `contracts/` entrypoint of each context in §1 is the extraction target — its port interfaces are already named in the "SOLE WRITER" + `domainDeps` columns and the §3 inversion mechanisms (`ToolExecution`, `ToolRegistry`, `SkillResolver`, `SkillRuntime`, `ModelRouter`, `MemoryRetriever`, `BudgetGuard`, `ObjectStore`, `ChannelAdapter`, `Notifier`, plus the kernel-hosted `DurableRuntime` / `EventBus` / `OutboxWriter` / `UnitOfWork` / `SafetyEventSink` / `ErasureTarget`). Start contract extraction at the leaves (`identity-access`, `secrets`, `files`, `durable-runtime`) and walk up the DAG to `conversations` last.

## 12. Amendment (M1) — the durable-runtime adapter directory carries no vendor segment

§4 and §5.1(h) above spell the durable-runtime adapter directory with a vendor
suffix. **The implemented directory is `packages/adapters/durable-runtime/`.**
Vendor identity lives inside the package — the `package.json` dependency entry,
the adapter class, and the package README — not in a path segment.

Why: the repository vocabulary boundary (WIN-292) scans repository *paths* as
well as file contents. `scripts/vocabulary-boundary.mjs` calls
`findForbiddenVocabulary(path, path, "path")` for every tracked file, so a
vendor-named directory segment yields exactly one reviewed manifest exception
**per file inside it**, permanently, and one more for every file ever added.
That is bookkeeping, not judgement: each row would restate the same fact about
the directory name and none would record a decision about code. Naming the
directory for the port it implements removes the whole class.

What is unchanged: the port (`DurableRuntime`), one-adapter-per-SDK containment,
this adapter's ownership of `internal-packages/database`, the composition-root
rule, and every other name in §4. §5.1(h) still binds the SDK to exactly one
directory — `scripts/arch/boundary-rules.mjs` holds that anchor as
`DURABLE_RUNTIME_ADAPTER` and `.dependency-cruiser.js` is generated from it, so
the two enforcers cannot disagree about which directory it is.

The same reasoning applies to any future adapter whose vendor name collides with
a reserved term: name the directory for the **port**, and name the vendor in the
code.

## 13. Amendment (M1 hand-off) — adapter-facing ports are context-owned

The M1 TypeScript project graph makes an ownership distinction that the accepted
layout and M2.1 hand-off did not state explicitly: an adapter-facing port belongs
to the context whose capability it serves. It does **not** move into the kernel
merely because its implementation lives under `packages/adapters/`.

The exhaustive M1 ownership map is:

| Adapter-facing port | Owning context |
|---|---|
| `TenancyRepository` | `tenancy` |
| `ObservabilitySink` | `observability` |
| `ObjectStore` | `files` |
| `RateLimiter` | `identity-access` |
| `ModelRouter` | `providers` |
| `ChannelAdapter` | `channels` |
| `Notifier` | `cost-monitoring` |
| `Cache` | `memory` |

Each interface is published from its owner's `application/ports` entrypoint.
Its adapter has one project-reference, workspace-dependency, and source-import
edge to that owner. `Cache` is intentionally owned by `memory`; Redis is an
implementation detail and does not define architectural ownership.

The kernel remains a pure leaf. Its cross-cutting decoupling ports remain exactly
`EventBus`, `OutboxWriter`, `UnitOfWork`, `Clock`, `IdGenerator`, `Logger`,
`DurableRuntime`, `SafetyEventSink`, and `ErasureTarget`. This amendment clarifies
the extraction hand-off; it does not rewrite the accepted context DAG, adapter
containment, or composition-root decisions above.

## 14. Amendment (M2) — the inference framework is a contained SDK, and the inference surface belongs on `ModelRouter`

§1 row 16 makes `conversations` the turn-execution engine, the sole writer of
`Thread`, `Turn`, `Step` and `PostmanExecution`, and the deepest node in the
DAG with eleven `domainDeps`. §11's hand-off says to walk up to it last. Two
things have to be true before it can be walked to at all, and neither was
stated above.

**The first: the inference framework is a vendor SDK, and §5.1(h) had not
named it.** The banned list in §2 and the containment list in §5.1(h) both name
raw provider clients (`openai`, `@anthropic-ai`). The running system does not
import those. It imports the cross-vendor framework above them — the `ai`
package and its `@ai-sdk/*` provider bindings — across twelve files under
`apps/agent/src`, which is where every model call in the product is made. A
context could have imported it and broken no rule.

`scripts/arch/boundary-rules.mjs` now carries `inference-sdk-only`, in the same
shape as every other (h) entry, with one home:
`packages/adapters/model-router-providers/` — the directory §5.1(h) already
pins the raw provider clients to, and the sole holder of the `ModelRouter`
implementation under §13. It is a SEPARATE id from `provider-sdk-only` rather
than a widening of it, because the two ban different layers and a reader of a
violation needs to know which they hit. `ai` is matched as a whole package
segment rather than as a prefix: every other entry in that file is a prefix,
which is safe for a distinctive scope and is not safe for two letters that also
open `airtable`.

The rule's from-side is every file that is not in that one home, which is
stricter than "`packages/contexts/**` may not". `scripts/arch/arch-boundaries.mjs`
judges it today across the whole V1 layout, and it is generated into
`.dependency-cruiser.js` from the same source, so the two enforcers cannot
disagree when that tool activates — as the note at the head of `boundary-rules.mjs`
records, dependency-cruiser is configured but not yet run in CI. Legacy
`apps/agent` remains outside the default scan during the strangler window,
exactly as §5.1(k)'s webapp lock is; the rule binds there when that tree moves
under the V1 layout.

The checker's specifier extractor was widened at the same time, and had to be:
it read `import x from "m"`, `import("m")` and `require("m")`, but not
`` import(`m`) ``. A template literal with no substitution in it is a static
specifier written in a different quote, so every ban in the §5.1 set — not only
this one — had a spelling that walked past it. Both dynamic forms are proved
against the real tree, not only against fixtures: adding `import { generateText }
from "ai"` and `await import("@ai-sdk/google")` to a real file under
`packages/contexts/providers/application/` each turn `inference-sdk-only` red
and each take the named case "the real repository scan is clean and
non-vacuous" with them.

**The second: a turn has to be runnable through a port.** A ban is only
honourable if what it forbids can be asked for somewhere else. §13 assigns
`ModelRouter` to `providers`; that port could resolve a route and probe a
credential, and could not run a turn. It now carries the inference surface as
well — `generate` and `stream`, over a request built from this repository's own
`Prompt`, `ToolDefinition`, `OutputMode` and `SamplingLimits`, returning its own
`ModelGeneration` and `GenerationEvent`. No vendor type appears in either
signature, which is not a matter of taste: under the rule above, one would make
the port unusable by the context it exists for.

Three consequences worth recording, because each was a choice:

- **The round trips are behind the port, not in front of it.** A generation runs
  until the model stops asking for tools or the step budget is spent, driven by
  a `ToolExecutor` the caller supplies. `providers` therefore learns a tool's
  name and its JSON Schema and nothing else, and gains no dependency on `tools`
  — its §1 row 4 allow-list is still exactly `tenancy` and `secrets`. The
  alternative, handing back one step at a time, would have moved the per-step
  prompt-cache placement onto every caller, and that placement is worth about
  three times the price of a long turn.
- **The prompt-cache rule is domain arithmetic.** `providers/domain/prompt-cache.ts`
  decides where breakpoints go, from the resolved route's dialect and a policy.
  It is pure, so it is unit-tested index by index rather than through a fake
  provider endpoint, and the adapter's job shrinks to mapping a marked message
  onto its provider's marker.
- **Cache accounting stays four-valued.** `TokenUsage` keeps its cache read and
  write counts separate through the port, because `ModelPrice` charges four
  rates. A surface that reported one input figure would have made a cached turn
  and an uncached one cost the same.

`conversations` is not extracted by this amendment, and the adapter behind the
port is still the generated placeholder. What changes is that the ban is
enforceable and the thing it forbids now has somewhere else to be asked for.

## 15. Amendment (M2.3) — one vendor client is one adapter DIRECTORY, and a directory may satisfy more than one port

§4's layout block above carries two sentences about `adapters/` that are not the
same sentence, and until WIN-258 tranche 2 the executable gates encoded the
narrower one.

The HEADER of the block says `adapters/ # each implements ONE port; sole holder
of its vendor SDK`. The BODY, on the very next line, says
`postgres-tenancy/ # Prisma tenancy-database client; per-context repos,
owner-tagged` — one directory, holding **every context's** repositories, each
row tagged with its owner. A directory cannot both implement one port and hold
per-context repositories for seventeen contexts. **The body is the decision and
the header is a summary of the common case.**

### Why the body wins

**Containment is decisive.** There is ONE PostgreSQL database behind ONE
generated client. Forty-three canonical-store ports across sixteen contexts sit
over it. If each context's repository were its own adapter package, the ORM
would have sixteen homes, and `tenancy-prisma-only` — the containment rule
tranche 1 had to invent, because before it *nothing in the repository pinned the
ORM to anywhere at all* — could not be written as a single-home rule. The gate
that exists only because this issue noticed it was missing would be undone by
the way this issue's next tranche was packaged. That is the whole argument.

**Ownership is not a package boundary here.** ADR §1 assigns each of the 93
canonical rows exactly one writing CONTEXT, and §2 forbids a context's `domain/`
and `application/` from importing the ORM. The rule that reconciles those two is
`CANONICAL_STORE_ADAPTERS` in `scripts/arch/table-ownership.mjs`, which records
per owner — by hand, never derived from the adapter table's owner column —
which directory writes on that owner's behalf. Ownership is carried by the owner
TAG and enforced by `checkSoleWriter` per WRITE. An owner with no entry in that
map still has exactly one permitted directory, so a shared directory is not a
blanket licence: a write to `Memory` from `postgres-tenancy` fails today and
will keep failing.

**The name refers to the database, not to the context.** `postgres-tenancy` is
the *tenancy-database* client — the name of the schema package it is the sole
holder of (`internal-packages/tenancy-database`). Holding `identity-access`'s
repositories is not the directory reaching outside itself; it is the directory
being what §4's body already called it.

**And one port could not have been implemented the other way.**
`AccessKeyStore.commitRotation` and `revokeAll` fence a rotation against a
concurrent revoke using `Environment.accessKeyRevocationVersion` — a column on
`Environment`, which `tenancy` owns. A separate identity-access adapter package
could not have bumped it without writing a row it does not own. The shared
directory can, because it is already `tenancy`'s delegate.

### What this amendment does NOT permit

It permits **many ports per directory**. It does not permit **any port from any
directory**, and the three gate surfaces were widened precisely so that the
difference stays checkable:

| gate | before | after | still refuses |
|---|---|---|---|
| `scripts/arch/gen-v1-skeleton.mjs` | one `ADAPTERS.length === 12` assertion standing for both "twelve directories" and "twelve bindings" | `EXPECTED_ADAPTER_COUNT` (12) and `EXPECTED_BINDING_COUNT` (13) as SEPARATE pins, plus per-binding owner validation, a per-directory duplicate refusal, and `MULTI_HOME_PORTS` | a 13th directory; a 14th binding; a binding whose owner is not a context or the kernel; the same port claimed twice; a port gaining a second home without being named |
| `apps/core-api/src/composition/adapter-bindings.ts` + `scripts/arch/composition-root.mjs` | `ADAPTER_BINDINGS` compared through a directory-keyed lookup; `PORT_SATISFACTION` keyed by directory and checked for PRESENCE only | both compared as SETS of `(adapter, port, owner)` in BOTH directions; `PORT_SATISFACTION` keyed `<adapter>:<Port>`, one entry per binding | an adapter satisfying a port it was not bound to (an unknown key now fails, where before an extra entry was invisible); a declared binding with no compile-time proof; a duplicated row |
| `scripts/arch/v1-project-graph.mjs` | `EXPECTED_ADAPTER_OWNERS` mapping each directory to ONE owner, giving it exactly one reference edge | values are ORDERED LISTS, compared exactly against the committed tsconfig references and manifest dependencies, with `EXPECTED_MULTI_OWNER_ADAPTERS` pinning which directory may have more than one and how many | an owner edge the directory was not granted; a granted edge that is missing; a second owner appearing anywhere it was not named; a repeated owner |

The one-port case is unchanged in every one of those tables: eleven of the
twelve directories declare a single binding and are judged exactly as they were.

**Every refusal in that table is a passing test, not a claim.** Fourteen of them
live in the gates' own mutation suites so they run on every change rather than
once, by hand:

- `scripts/arch/gen-v1-skeleton.test.mjs` — six cases, driven through
  `checkAdapterTable(adapters)`, which takes the table as an ARGUMENT so a
  mutation is a value rather than an edit to the module.
- `scripts/arch/composition-root.test.mjs` — four cases over a real-tree copy,
  including the one the directory-keyed table could not see at all: an EXTRA
  `PORT_SATISFACTION` entry proving a pair nobody bound.
- `scripts/arch/v1-project-graph.test.mjs` — four cases through
  `checkAdapterOwnerCounts(owners, multiOwner)`.
- `scripts/arch/sole-writer.test.mjs` — three cases: the shared directory may
  write both owners' rows and nothing else, and `redis-ratelimit` — also owned
  by `identity-access` — still may not write `User`, because the delegation is
  granted per OWNER and never derived from the adapter table's owner column.

### Consequences recorded here rather than discovered later

- The V1 project edge count moves **95 → 96**: `packages/adapters/postgres-tenancy`
  gains a second owner reference, to `packages/contexts/identity-access`. It
  cannot create a cycle — nothing imports an adapter except the composition
  root, and `tenancy` already depends on `identity-access` under §1.
- The adapter count stays **12** and the reachability canary stays at **117**
  (`97 scaffolding + 20 placeholder`): no package is adopted, so no placeholder
  is released.
- `Notifier` remains the one port with two adapters (`notifier-email`,
  `notifier-webhook`) — that direction of many-to-one was always ADR §4's own
  case, and it is now written down as `MULTI_HOME_PORTS` rather than tolerated
  by a check that never looked.
- The remaining fifteen contexts' canonical-store repositories (tranche 5) land
  in this same directory. That is the design, not a later exception: at the end
  of M2.3 there are still twelve adapter directories and one home for the ORM.

## 16. Amendment (M2.5) — the ambient environment has one reader per deployable

**WIN-260 (M2.5).** Its acceptance opens with a sentence that was TRUE and
enforced NOWHERE: *feature code does not read `process.env`.*

### The position this rule was in

§15 records why `tenancy-prisma-only` had to be invented in M2.3: `@prisma` was
on the §2 banned list for `domain/` and `application/`, so a context's core could
not import it — and **nothing said where it COULD live**. A transport, a second
adapter or the composition root could all have held the ORM client with every
gate green, because a purity rule is not a containment rule.

The ambient environment was in exactly that position, one layer up. No rule in
this repository had ever looked at it. The measurement at `f88c8364`:

| Where | Environment reads | What they are |
|---|---|---|
| `packages/kernel/**` | 0 | — |
| `packages/contexts/**` | 0 | four files MENTION `process.env` in prose, in domain-policy banners explaining why a limit is a parameter |
| `packages/adapters/**` | 16 | all in real-PostgreSQL harnesses spawning the ORM's migration CLI |
| `apps/core-api/**` | 3 | one inline in `main.ts`, two in the executable process evidence |
| `apps/mcp-stdio/**` | 2 | one inline in `main.ts`, one in its executable evidence |

Two of those twenty-one were **feature code**: one line in each deployable's
`main.ts`. Neither was wrong, and neither was pinned, so the property was one
line away from being false in a package nobody would think to check.

### The rule

`scripts/arch/env-access.mjs`, in the release-gate list beside
`audit:composition-root`:

- **One declared reader per deployable**, in a file that does nothing else:
  `apps/core-api/src/config/environment.ts` and
  `apps/mcp-stdio/src/environment.ts`. Each takes ONE frozen snapshot at startup
  and hands it on as an ordinary value; every configuration module below is a
  pure function over that value.
- **The exception is a FILE LIST, not a directory.** A directory-shaped allowance
  grows a second reader the week after it is written and nothing goes red.
- **Every test-support read is pinned to an exact count, in both directions.** A
  file that gains one fails; a file that loses one fails too, so a pin cannot
  outlive the read it describes and quietly license a future one.
- **Fail closed on what cannot be attributed.** A computed key on the process
  object cannot be shown to be `env` or shown not to be, so no file may do it —
  a declared one included. This is the axis §5.2's sole-writer lint records after
  six of seven spellings of a Prisma write turned out to be invisible to a
  matcher that only knew the literal one.

### Why the two deployables do not share a reader

Rule (j) `adapters-only-from-core` makes `apps/core-api` the single composition
root, and `apps/mcp-stdio/src/runtime.ts` records at length why that binary must
not reach into that tree. Importing the core-api package into the stdio binary
would also pull an HTTP framework into a process that speaks over a pipe. Two
deployables, two process edges, one read each — and the count is two, stated,
rather than a directory nobody re-reads.

### What this amendment does NOT claim

- **It does not scan the legacy tree.** `apps/agent`, `apps/webapp`,
  `packages/core` and `internal-packages` hold 526 environment reads between them
  at `f88c8364`. They are the tree M2 is extracting FROM. §6's `max-file-lines`
  states the same reasoning for the same directories: pointing a rule at code
  this programme does not own produces a wall of findings nobody can act on,
  which is how a gate stops being read.
- **It does not make the five new configuration sections load-bearing yet.** They
  are validated at startup and refused at the process boundary; the composition
  root still CONSTRUCTS no adapter, exactly as `app.module.ts` says. Config
  presence and adapter supply become one decision when the root constructs.
- **It is name-driven, not type-driven.** Any expression spelled `process` is
  assumed to be the Node process, and a local named `process` that is not one
  will fail. That direction is deliberate for a containment gate; §5.2 states
  the same contract for a receiver spelled like a Prisma delegate.

### Consequences recorded here rather than discovered later

- The scanned V1 source census moves **1493 → 1503**: seven configuration modules
  and two suites under `apps/core-api/src/config/`, and one environment reader
  under `apps/mcp-stdio/src/`. `arch-boundaries`, `composition-root` and
  `env-access` all read that number back from their own scans of the same five
  roots, so the three can DISAGREE and be caught.
- `max-file-lines` does **not** move: its selectors cover
  `apps/core-api/src/transports/**`, and none of these files is a transport.
- `test-case-census` does **not** move: its package roots are
  `packages/{kernel,contexts,adapters}`, and `apps/core-api` is not among them.
- The V1 release gate list moves **24 → 26** and the CI semantic mutation control
  table **359 → 361**, two controls per new gate, on the same terms §15's
  composition-root pair moved them.
