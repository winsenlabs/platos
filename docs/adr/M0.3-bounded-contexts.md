# ADR M0.3 — Bounded-Context Decomposition & Dependency Direction for Platos V1 (WIN-248)

**Status:** **ACCEPTED (with qualification), 2026-08-28** · **Supersedes:** nothing · **Feeds:** M2.1 (extract domain contracts), M2.2 (BFF Prisma removal)

> **Immutable evidence.** This ADR is accepted and frozen. Do not edit accepted decisions in place — a future architectural change is recorded in a new, superseding ADR that references this one. The decision record is §7.

**Synthesis basis:** Spine = the canonical-store-write-ownership decomposition (score 31/40; top on ownership-clarity 9 and charter-fit 9). Grafted, per judge guidance: (a) from the capability-vertical proposal — the *sole-writer lint extended from the existing `clean-prisma-delegates.test`*, the *identity-isolation import denylist*, and *kernel-hosted decoupling ports* (`SafetyEventSink`, `ErasureTarget`, `DurableRuntime`) to kill fan-in cycles; (b) from the lifecycle-layer proposal — the *kernel-as-true-leaf rule* and the *reader-port dependency-inversion* pattern applied selectively at read-seams. Three latent cracks the judges found in the spine are fixed here: `ToolCall` sole-writer contradiction, the `privacy ↔ everyone` fan-out, and the leaked-Prisma-txn outbox.

## 1. Decision — the bounded contexts

**Cutting rule:** every canonical row has exactly **one** context permitted to write it; every external system (Trigger DB, ClickHouse, MinIO, Redis, provider APIs, channel APIs) is reached only through a Platos-owned port whose adapter is the *sole* holder of that vendor SDK. Where two current modules co-write the same tables they are **one** context (→ `tool-gateway` + `mcp-platform` merge into `tools`); where one module writes tables of three owners it is **split** (→ `monitoring` splits into `cost-monitoring` / `governance` / `observability`).

**Count: 17 domain contexts + 1 infrastructure adapter-context (`durable-runtime`) + 1 shared-kernel package (`platform-kernel`) = 19 packages.** This granularity is deliberate: the spine's 785-capability matrix and the two 7k monoliths do not collapse into 4–5 contexts without re-creating a god-module (the lifecycle-layer alternative's `runtime-core` openly "risks re-congealing into the very agent.service monolith"). Finer than ~17 mostly adds thin packages; the genuinely mergeable pairs are surfaced as founder decisions (§7) rather than pre-decided.

Every other context is a narrow, single-owner slice. The three broadest capabilities the old `monitoring` conflated are deliberately three contexts (13/14/12).

## 2. Dependency-direction ADR

**Onion, per context.** Each of the 17 domain contexts and `durable-runtime` is a package with exactly these layers, and imports point **inward only**:

```
transports (REST / MCP / WS / webhook / channels-ingress / BFF)
  → application (commands / queries / use-cases)      ── define the ports
    → domain (entities, value objects, events)
      ← adapters (Prisma / Redis / ClickHouse / MinIO / providers / channels / Trigger)  implement ports, depend INWARD
```

- `application` may import `domain`. `domain` may import nothing but `platform-kernel`.
- `adapters` and `transports` may import that context's own `application` + `domain` + `platform-kernel` — **never** the reverse; `domain`/`application` must never import `adapters` or `transports`.
- **Cross-context:** a context may import another **only via that other context's published contracts (ports + DTOs + integration events)** — never its `domain`, `application`-internals, or `adapters`. The allowed edge-set is exactly the `domainDeps` DAG in §1.
- **Reader-port inversion (selective graft):** where an upstream owner must *drive* a downstream engine (channel inbound → start a turn; tool "run-agent-as-tool"), the arrow is **never** owner→conversations. It inverts through the kernel `DurableRuntime`/`EventBus` seam (job enqueue or event), keeping `conversations` a sink.

**Banned imports in `domain/**` and `application/**` of every context (the charter purity rule):**

```
@nestjs/*        prisma / @prisma/* / any generated prisma client
ioredis / redis  @clickhouse/*        minio / @aws-sdk/*
@trigger.dev/*   @modelcontextprotocol/*
openai / @anthropic-ai/* / any provider SDK
```

Domain and application see infrastructure **only** as Platos-owned port interfaces from their own `application/ports` or from `platform-kernel`. This is the charter's non-negotiable list, enforced mechanically in §5.

## 3. Cycle-destination table (acceptance criterion)

Every real cycle and wrong-way edge from the M0.1/M0.2 ground truth, with a concrete destination. **All 8 have a landing site; none is hand-waved.**

| Ground-truth edge (files) | Side A lands in | Side B lands in | Inversion mechanism |
|---|---|---|---|
| **agent-runtime ↔ mcp-platform** (1 / 3) | runtime → **conversations** | mcp → **tools** (merged) | Forward: `conversations → tools` via `ToolExecution` port. The 3 reverse imports ("run agent as MCP tool"/subagent) become a **`DurableRuntime` job** (`/internal/subagent-turn`), not a code edge. |
| **agent-runtime ↔ tool-gateway** (5 / 2) | runtime → **conversations** | gateway → **tools** | The 5 forward calls internalize behind `ToolExecution`/`ToolRegistry` ports. The 2 back-edges (`execute-as-agent`, stream callback) become a **durable subagent job hop + a `TurnMessage` event**. No import back into conversations. |
| **agent-runtime ↔ channels** (2 / 2) | runtime → **conversations** | **channels** (own context) | No direct edge either way. Inbound: channels writes `ChannelEventInbox`, **enqueues a turn job via `DurableRuntime`**. Outbound: channels **subscribes to the `OutboundAssistantMessage`/`TurnMessage` event**. The 2 channel controllers physically move into `channels/transport`. |
| **agent-runtime ↔ skills** (3 / 1) | runtime → **conversations** | **skills** (own context) | Forward: `conversations → skills` via read-only `SkillResolver` + `SkillRuntime` ports (3 calls). The 1 back-edge: shared type **hoisted to `platform-kernel`**; any skill-initiated run routed through a **`DurableRuntime` job**. |
| **mcp-platform ↔ tool-gateway** (3 / 2) | **tools** (merged) | **tools** (merged) | **Collapsed** — both are sole co-writers of `Tool`/`ToolHealth`/`EntityMcp*`, so they become ONE context; the 3+2 imports are now intra-context. **Internal direction is enforced one-way:** `mcp-dispatch → tool-registry`, never the reverse (closes the residual-module-cycle crack the judge flagged). `McpToken`/`McpBearerToken` writes relocate to **identity-access**. |
| **auth → tool-gateway** (2 files: `auth.service`→`ToolRegistryService`, `auth.module`→`ToolGatewayModule`) | **identity-access** (leaf) | **tools** | **Physical delete.** Remove the `ToolRegistryService` import from `auth.service.ts` and `ToolGatewayModule` from `auth.module.ts`. Tool↔scope validation moves to execution time **inside tools** (`tools → identity-access` for scopes, one-way). identity-access **never** imports tools — locked by the identity-isolation denylist (§5). |
| **auth → providers** (4 files: `provider-health.service` inside auth) | **identity-access** | **providers** | **Physical move.** `provider-health.service.ts` (+ test) leaves auth for `providers`, beside `PROVIDER_MANIFESTS` + `ScopedEnvService`. identity-access drops the `ProvidersModule` import. Edge vanishes (intra-context). |
| **auth → monitoring** (1 file: `rate-limit.guard`→`SafetyEventService`) | **identity-access** | **governance** | **EventBus inversion via kernel port.** `rate-limit.guard` publishes a `SafetyEvent` domain event through the kernel **`SafetyEventSink`** port; `governance` implements the sink, is sole writer of `SafetyEvent`, wired at the composition root. No identity→governance code edge. |

**Two self-introduced cycles the judges flagged in the source proposals, pre-empted here:**

- **`privacy ↔ everyone` fan-in/out.** Neither "privacy defines a port everyone implements" (fan-in cycle) nor "privacy imports every context" (10-way fan-out). Instead **`ErasureTarget` is a kernel-hosted port**; each context implements it for its own rows; the composition root injects `ErasureTarget[]` into privacy. `privacy` depends on `tenancy + kernel` only.
- **Leaked-Prisma-txn outbox.** No context passes a Prisma txn handle across a port. `platform-kernel` defines `UnitOfWork` + `OutboxWriter`; producers call `OutboxWriter.append(event, uow)` inside their own `UnitOfWork`; the **kernel outbox adapter is the single physical writer** of the `Event` table; `observability` and `eventing` are drain-side consumers. One transactional outbox, multiple drains (§7.8).

### 5.2 Sole-writer lint — extend the existing `clean-prisma-delegates.test`

The repo **already has** `clean-prisma-delegates.test`; extend it with a checked-in ownership map (the §1 SOLE-WRITER column) and assert that mutating delegates for a model appear only under its owner:

```ts
// contexts/_meta/table-ownership.ts  (single source of truth, also feeds dependency-cruiser (d))
export const OWNER: Record<string, Context> = {
  User: 'identity-access', /* … */ Entity: 'tenancy',
  ToolCall: 'tools', ToolCallAudit: 'tools', SafetyEvent: 'governance',
  Thread: 'conversations', Turn: 'conversations', Step: 'conversations',
  Budget: 'cost-monitoring', AdminAudit: 'observability', Event: '<kernel-outbox-adapter>', /* … all rows */
};
const MUTATORS = /\.(create|createMany|update|updateMany|upsert|delete|deleteMany)\b/;
// FAIL if a file under packages/(contexts|adapters)/<X> calls a MUTATOR on prisma.<model>
//      whose OWNER[<model>] !== <X>.  Reads (findMany/findUnique) are exempt.
```

This converts the ownership map and every wrong-way edge from aspiration into a non-regressable gate, independent of context count.

### 5.3 Kernel-content assertion

A tiny AST test over `packages/kernel/src/**`: fail if any file declares a class with a non-empty constructor, imports anything outside `packages/kernel`, or exports a value that is not an interface / type alias / const enum / frozen object / pure function. This is what keeps the shared kernel from becoming a junk drawer while it hosts `DurableRuntime`/`SafetyEventSink`/`ErasureTarget`.

## 6. File-size / complexity budgets

The 7.1k `agent.service.ts` + 7.0k `agent.controller.ts` are the failure these budgets exist to prevent. Enforced by ESLint (fails CI) plus one custom check.

`.eslintrc` (applies to `packages/contexts/**` and `apps/core-api/src/transports/**`):

| Budget | Value | Rule |
|---|---|---|
| Max lines per file | **500** hard error (warn at 400) | `max-lines: [error, {max:500, skipBlankLines:true, skipComments:true}]` |
| Max lines per function/method | **80** | `max-lines-per-function: [error, {max:80, skipComments:true}]` |
| Cyclomatic complexity per function | **15** | `complexity: [error, 15]` |
| Constructor-injected deps per class | **6** (warn), **8** hard | `max-params` on constructors + custom `max-injected-deps` |
| Nesting depth | **4** | `max-depth: [error, 4]` |
| **Routes per controller** | **12** | custom `max-routes-per-controller` (counts `@Get/@Post/@Put/@Patch/@Delete/@MessagePattern` decorators per class) |
| Public methods per application service | **10** (warn) | custom `max-public-methods` |

Two structural corollaries:
- A turn's orchestration in `conversations` must be split into **named sub-use-case files** (prompt-build, tool-loop, structured-output, multimodal, compaction, dispatch), each ≤500 lines — the `max-lines` wall is the package-internal equivalent of the boundary the lifecycle-layer proposal admitted its `runtime-core` lacked.
- `BudgetService` (18 methods) exceeds the 10-public-method budget and must be split (e.g. `BudgetPolicy` / `BudgetLedger` / `BudgetGuard`) when it lands in `cost-monitoring`.

Budgets are advisory-warn during the strangler migration and flip to hard-error per package as each context is extracted, so legacy `apps/agent` files do not block unrelated work but no *new* monolith can form.

## 7. Decision record (ACCEPTED 2026-08-28)

All ten decisions below are **accepted as recommended**, with one qualification:

> **Decision #9 (sync → async on reverse edges) — accepted WITH qualification.** Durable job hops are accepted for the internal reverse flows (subagent / execute-as-agent / MCP-tool-as-agent). **BUT any existing synchronous API must retain its observable result/error semantics through an enqueue-and-wait compatibility façade** — the caller still receives the terminal result or error, not an accepted-and-detached acknowledgement. **No silent conversion to fire-and-forget.** The async default applies to the internal execution mechanism; the external contract remains synchronous where it is synchronous today.

Decisions 1–8 and 10 are accepted exactly as recommended below. The recommendations are retained as rationale.

---

Genuine judgment calls where reasonable architects differ. Each: options → recommendation.

1. **identity-access and tenancy: two contexts or one?** The lifecycle-layer proposal merged them into a single `kernel-identity-tenancy` leaf. **Options:** (a) two contexts, identity-access as the leaf, `tenancy → identity-access`; (b) one merged leaf. **Recommend (a).** Splitting keeps ownership crisp (auth tokens vs. the tenant tree are different change-cadences) and the leaf rule on `identity-access` alone already kills all three wrong-way auth edges — merging buys nothing the isolation lint doesn't already give.

2. **Overall granularity — keep 17 domain contexts or consolidate the thin ones?** Thin candidates: `secrets`, `eventing`, `jobs`. **Options:** keep all; or fold `secrets→providers`, `eventing→cost-monitoring`, `jobs→durable-runtime`. **Recommend keep `secrets` and `jobs` separate** (secrets is the encryption boundary — collapsing it tempts providers to write ciphertext directly; jobs is the Platos-side approval/record seam distinct from the Trigger adapter), **and consider merging `eventing`'s notification routing into `cost-monitoring`** only if notifications stay alert-shaped. Revisit after M2.1 sizing.

3. **Where `BudgetService` lands, and where enforcement runs.** Ownership: `cost-monitoring` (recommended, spine). But `BudgetGuard` pre-spend check is on the **hot turn path** — the lifecycle-layer proposal's version put budget reads top-of-stack and dented latency. **Options:** (a) `conversations` calls `cost-monitoring.BudgetGuard` synchronously (fresh, +1 read/turn); (b) `BudgetGuard` reads a cached cap + async-reconciles spend. **Recommend (b)** — cached guard, exact reconcile off the outbox.

4. **`ToolCall` sole-writer — `tools` or `conversations`?** Source proposals contradicted each other here. **Options:** (a) `tools` writes `ToolCall`+`ToolCallAudit` (executor owns the execution record); `conversations` writes a `Step` that references it. (b) `conversations` owns `ToolCall` as part of the turn transcript. **Recommend (a)** — the executor is the writer; keeps single-writer crisp. Reversible via the ownership map without moving code between contexts other than the repo.

5. **`AgentSkill` binding — `agents` or `skills`?** **Options:** (a) `agents` owns it (loadout is part of the agent version), `agents → skills` one-way; (b) `skills` owns it, `skills → agents`. **Recommend (a)** — treats loadout as authoring, and it is the direction that keeps `skills` a lower, more-reused context. Genuinely flippable; flipping moves one write-owner and one DAG edge.

6. **`Entity` — `tenancy` or `channels`?** The spine placed a channel-`Entity` in channels; the charter capability list groups `entity` under tenancy. **Options:** (a) `Entity` is the tenant-tree leaf in `tenancy`, channels references it by id; (b) channels owns a `ConnectedEntity`. **Recommend (a)** — bindings across many contexts key off Entity; it must be structural, not channel-specific.

7. **Does the `webapp` Remix BFF survive, or get absorbed into `core-api`?** **Options:** (a) BFF survives as a Remix transport; M2.2 removes its 117 direct-Prisma loaders/actions so all data flows through `core-api` query ports; (b) absorb the BFF into `core-api` transports outright. **Recommend (a)** now — smaller blast radius, keeps the single deployable, and the `webapp-no-prisma` lint (§5) enforces the M2.2 migration. Absorption is a later, optional call once the query-port surface is stable.

8. **One transactional outbox or two?** The spine had a separate `ObservabilityOutbox`; this synthesis unifies on the single kernel `OutboxWriter` with multiple drain consumers (`observability` projection, `eventing` notifications). **Options:** (a) one outbox, split the *drain* if volume demands; (b) two physical outboxes from day one. **Recommend (a)** — one write path removes the leaked-txn violation; split reads later if ClickHouse projection volume warrants.

9. **Accept the sync→async behavior change on reverse edges?** The subagent / execute-as-agent / MCP-tool-as-agent paths convert synchronous returns into `DurableRuntime` job hops that **park on a waitpoint** — a real failure-model change, not a mechanical move. **Options:** (a) accept async everywhere (durable, but changes latency + error semantics, needs correlation-id tracing); (b) keep a synchronous in-process fast-path port for latency-critical MCP tool calls, async for the rest. **Recommend (a) as default, (b) only if a measured latency SLO forces it.** This is the one place the migration is behavior-changing and warrants explicit sign-off.

10. **`durable-runtime` owns the entire Trigger DB behind one port.** **Options:** (a) full encapsulation — no domain context touches `internal-packages/database`, everything goes through `DurableRuntime`; (b) leave Trigger tables partially visible for ops queries. **Recommend (a)** — it is what makes "one deployable, Trigger behind a port" true and keeps the SDK containment lint meaningful.
