# M2.5 — transaction and outbox semantics, clock and retry policies, graceful shutdown

WIN-260, on top of WIN-258 (M2.3). This is the operator-facing statement of four
contracts the code now enforces, and an honest account of what it does not yet
cover. Every number here is read back from the tree, not asserted at it.

---

## 1. An error `Result` never commits the frame that produced it

`UnitOfWork.run` commits when its callback RESOLVES and rolls back when it
REJECTS. That is the only contract a transaction can have. Every use case in this
tree reports failure as a `Result` VALUE — deliberately not a thrown class, so a
failure path is type-checked rather than discovered. The two contracts collide:
a callback that returns `{ ok: false, error }` has resolved, and therefore
commits.

`cost-monitoring` shipped exactly that. `detect-crossings` wrote a threshold
event, fanned out one alert delivery per subscribed channel, and returned the
fan-out's error `Result` from inside the callback. The crossing committed; no
delivery row landed beside it; the `@@unique([budgetId, windowKey, threshold])`
constraint then refused the crossing for ever after. A budget alert had fired and
would never be sent. Every test was green, because an in-memory double has no
commit to observe.

**The contract.** `runResult(unitOfWork, work)` in
`packages/kernel/src/ports/unit-of-work.ts` is the sanctioned way to end a unit
of work with a failure. `ok` commits; `err` ROLLS BACK and comes back unchanged —
the same error value, so a caller matching on `error.code` sees what the
repository actually said. Inside `runResult` the failing branch throws before any
`return` is reachable, so "commit with an error" is not a thing that can be
written there.

**The nested case, stated rather than overclaimed.** `run` JOINS an open
transaction rather than opening a second one, so a `runResult` inside another has
no boundary to roll back to. Its abort unwinds to the joined callback's caller as
a value. If that caller propagates it, the outer `runResult` aborts the real
transaction and everything is discarded. If it deliberately swallows it and
returns `ok`, the outer transaction commits — a decision taken in the open, at a
call site a reader can see, and the only shape that leaves room for a use case
that genuinely tolerates a partial failure.

The property that holds unconditionally is the one that was violated:
**an error `Result` never commits the frame that produced it.**

**The abort is a branded plain object**, not an `Error` subclass: ADR M0.3 §5.3
forbids the kernel from declaring a class with a non-empty constructor. The brand
is a STRING and not a symbol, because two resolved copies of `@platos/kernel` in
one process — the ordinary state of a workspace mid-migration — would mint two
symbols, and a symbol-identity check would fail OPEN, rethrowing a business abort
as a defect and turning a rolled-back use case into a 500.

**Adoption is partial and the remainder is named.** `cost-monitoring`'s
`detect-crossings` — the one place that shipped the defect — now calls
`runResult` and its bespoke `CrossingFanOutFailed` class is gone. Elsewhere,
**111 `unitOfWork.run` call sites across 67 files** still use the
commit-on-resolve form. Converting them is mechanical but it is not small, and it
is a behavioural change at every site (an `err` that used to commit will roll
back). It is stated here as the remainder rather than half-done.

## 2. Time is an input

ADR M0.3 §4 declares a `Clock` port and every context's `dependencies.ts` takes
one. Four of them say so outright — `tenancy`'s reads "Time and identity are
PORTS, not ambient functions. No `new Date()` and no random identifier back
inside a use case." All four statements were PROSE. Nothing checked them.
`scripts/arch/boundary-rules.mjs` could not: it is an import-graph checker and
`Date` is a global, so there is no import to ban.

`scripts/arch/ambient-time.mjs` is the check. It is an AST walk over the
TypeScript parser — not a regex, because four context headers contain the
sentence "no `new Date()`" and a regex gate would fail on the prose describing
the rule it enforces.

| rule | refuses | substitute |
| --- | --- | --- |
| `T1` | `Date.now()` | the `Clock` port |
| `T2` | `new Date()` with NO argument | the `Clock` port |
| `T3` | `performance.now()` | an adapter; a monotonic reading is still a reading |
| `T4` | `Math.random()` | the `IdGenerator` port |
| `T5` | `setTimeout` / `setInterval` / `setImmediate` | an adapter |

`new Date(value)` stays legal: a use case that could not name any instant could
not name the one the Clock handed it. A type position naming a scheduler
(`ReturnType<typeof setTimeout>`) is not scheduling.

**Scope.** `packages/contexts/*/{domain,application}`, tests included. Adapters
are deliberately out: an adapter is where infrastructure lives, `process-ports.ts`
implements the `Clock` with `new Date()` and must, and an exception list is how a
gate stops meaning anything. `packages/kernel` is out because
`scripts/arch/kernel-content.mjs` rule K4 already holds it to a stricter bar, and
one violation should not have two names in two reports.

**It was not vacuous.** The first run reported **ten** violations, every one a
fixture in a domain or application suite writing `new Date()` for an `archivedAt`
or a `quarantinedAt` — tests whose values depended on when they ran. All ten are
now fixed instants. Tests are held to the same bar as the code under test rather
than exempted: a suite that cannot place an instant deliberately is a suite that
cannot catch what `governance` caught when version attribution stamped the live
binding instead of the version under review.

## 3. Retry is bounded, and the bound is stated

Four retry schedules already existed and no two were written alike:

| context | shape | bound stated? |
| --- | --- | --- |
| `eventing` | `min(2^retryCount × 1000, 30000)`, `MAX_RETRIES = 3` | per wait only |
| `cost-monitoring` | flat `retryBackoffSeconds` on the delivery terms | no |
| `observability` | a drain pass bounded by rows and wall clock | per pass |
| `privacy` | an erasure sweep re-run | no |

Each is right for its own queue. None could state the number an operator actually
needs: the TOTAL. Unbounded growth turns a downstream outage into a queue nobody
can drain — the tail's next send is scheduled beyond the retention window, the
row is pruned before it is ever sent again, and a failure becomes silent data
loss.

`packages/kernel/src/vo/retry.ts` is the value object. A policy is
`{ maxSends, baseDelayMs, multiplier, ceilingMs, jitterFraction }`, minted only
through `defineRetryPolicy`, which refuses five different mistakes with five
distinct codes:

| code | refuses |
| --- | --- |
| `RETRY_POLICY_MAX_SENDS_INVALID` | fewer than one whole send |
| `RETRY_POLICY_BASE_DELAY_INVALID` | a negative or fractional first wait |
| `RETRY_POLICY_MULTIPLIER_INVALID` | growth below 1, or not finite |
| `RETRY_POLICY_CEILING_BELOW_BASE` | a ceiling under the policy's own first wait |
| `RETRY_POLICY_JITTER_FRACTION_INVALID` | a jitter band outside `[0, 1]` |

Five codes and not one, because they are five different fixes and an operator
should not have to read the source to learn which they made.

* `backoffMs(policy, retryCount)` is `min(base × multiplier^retryCount, ceiling)`.
  The exponent is the RETRY number, so the first retry already carries one factor
  of growth — the surprising half of the legacy `eventing` schedule, preserved
  because changing it would silently halve every existing backoff.
* `totalDelayCeilingMs(policy)` is `(maxSends − 1) × ceilingMs`: **the bound, as
  arithmetic.** Compare it against the retention window on the queue. If it is
  larger, the last retry is scheduled after the row is pruned and the retry
  budget is a fiction.
* `jitteredDelayMs` only ever SUBTRACTS, so a jittered schedule can never exceed
  the un-jittered bound. Jitter takes the random draw as a PARAMETER: nothing in
  the kernel calls `Math.random()`, so a suite reads the exact edges of the band
  and production passes a real draw.
* A draw outside `[0, 1]` is CLAMPED, not refused. This runs on the retry path,
  and refusing to schedule because a random number was out of range would turn a
  bad draw into a lost message.

**It is joined to the schedule that ships.**
`packages/contexts/eventing/domain/retry-schedule.kernel-conformance.test.ts`
declares the kernel policy to BE `eventing`'s live schedule and sweeps 64 retry
numbers across every observable of both. Every field of the declaration is READ
from `retry-schedule.ts` rather than typed as a literal, so the two cannot drift
apart with that suite green. The one disagreement is named rather than tolerated:
`backoffMs(0)` answers 1000 in the legacy formula and 0 in the kernel, for a
retry number no decision can reach, and a case proves it is unreachable on both
sides.

`eventing`'s shipped schedule is UNCHANGED. Nothing was rewritten on the strength
of an argument that the two agree — that claim is what the conformance suite
proves, and re-expressing the other three contexts over the policy is remaining
work.

## 4. Shutdown refuses, then drains, inside ONE budget

The order in `apps/core-api/src/runtime/lifecycle.ts`:

1. flip readiness to `draining`, so `/readyz` answers 503 while the listener is
   still up;
2. keep serving for `drainGraceMs`, so a balancer polling `/readyz` can observe
   (1) and stop routing here;
3. **close admission** — every request from here on is refused, not begun;
4. stop accepting connections, release idle keep-alive sockets;
5. drain in-flight work, bounded by `shutdownTimeoutMs`;
6. **drain deferred work** — the outbox first — out of what is LEFT of that same
   budget;
7. release every remaining socket, then close the framework.

**Step 3 exists because `server.close()` is not the same act.** It refuses new
CONNECTIONS and says nothing about a keep-alive connection an upstream proxy
already holds. Such a connection can deliver a request after the drain has
counted zero; it is routed, begun, and destroyed at step 7 — work accepted and
silently dropped, which is strictly worse than work refused, because a refusal is
retriable and a reset in the middle of a non-idempotent write is not. The refusal
is 503 with `Connection: close`, `Retry-After: 1`, and
`core-api.shutdown.work_refused` — a DISTINCT code from the readiness 503,
because "route elsewhere, this instance is not ready" and "this instance is going
away, the request was never begun" are different operator responses.

**Step 6 exists because the outbox row is emitted LATER.** It is written inside
the transaction that wrote the state it describes, which is what makes emission
atomic; the other half of that bargain is that a drain carries it out. At the
moment a process stops, the rows written by the requests it has just drained are
sitting in the table with nobody holding them. Exiting there is correct and it is
SLOW: nothing is lost, but every event waits for whichever process next runs a
drain, and during a rolling restart of a whole fleet that can be the far side of
the restart.

**One budget, divided.** `shutdownTimeoutMs` is what the orchestrator gives
before SIGKILL. Two `await`s with that timeout spend it TWICE and guarantee the
second drain is killed mid-flush. `shutdown-drain.ts` hands each step what is
LEFT, measured on the injected clock; does not CALL a step that arrives with
nothing; races every step against its own slice so a drainable that ignores its
budget cannot take the whole shutdown; and carries on past a step that throws,
because the outbox flush matters most on a bad day.

| code | means |
| --- | --- |
| `core-api.shutdown.drain_name_taken` | two drainables answer to one name; their two rows would be one row |
| `core-api.shutdown.drain_budget_spent` | the step was never called: the budget was already gone |
| `core-api.shutdown.drain_timed_out` | the step ran and did not finish inside its slice |
| `core-api.shutdown.drain_faulted` | the step rejected; the sequence continued |

**One verdict over both halves.** A process that drained every request and
abandoned a full outbox has not shut down cleanly. `StopOutcome.drained` is the
AND of the two, and `main.ts` turns it into the exit code an orchestrator reads.

**The outbox flush.** `packages/adapters/outbox/src/flush.ts`, not the process
edge. It was drafted under `apps/core-api/src/runtime/` and
`scripts/arch/composition-root.mjs` refused it: rule (C1) allows exactly ONE
importer of an adapter package, and that is `adapter-bindings.ts`. The refusal
was right beyond the letter — everything the loop knows is outbox knowledge (a
cursor is a PAIR because two rows share a millisecond; a SHORT page is not the
end and only an EMPTY one is; a null cursor accompanies an empty page) and a copy
of that at the process edge would be a second place to get it wrong.
`OUTBOX_FLUSH_SATISFACTION` in `adapter-bindings.ts` proves the flush is the
`Drainable` the sequence drains, beside `OUTBOX_STORE_SATISFACTION`.

It is AT-LEAST-ONCE and says so: the handler sees a page before the cursor
advances past it, and the cursor lives only in that call. `Event` has no
`deliveredAt` and no `status` column, because ADR M0.3 §7 decision 8 chose one
physical outbox behind several drains, each holding its own position. A flush
claiming exactly-once would be claiming a column the table does not have.

**What is NOT wired.** `StartOptions.drainables` is EMPTY in every install this
repository composes. The flush is built and proven; it has no production handler
to hand pages to until M4 wires the projection and notification drains. That
absence is stated as an absent drainable rather than as a drain that reads pages
and drops them.

## What remains

* **111 `unitOfWork.run` call sites** in 67 files still use the
  commit-on-resolve form (counted at HEAD with
  `grep -rn "unitOfWork.run(" packages/contexts/*/application --include="*.ts"`,
  excluding test doubles and suites). `runResult` exists and one context is converted.
* **Three of the four retry schedules** (`cost-monitoring`, `observability`,
  `privacy`) are not yet expressed over `RetryPolicy`; only `eventing` is joined
  to it, and by conformance rather than by rewrite.
* **No production drainable is wired.** The outbox flush needs M4's projection
  and notification consumers before `drainables` is non-empty in a real process.
* **`NotResult<Value>`** states the rule at the type level and is not yet
  enforced on `UnitOfWork.run`'s signature; doing so is what would make the
  commit-on-resolve form unwritable rather than merely unsanctioned, and it
  cannot land before those call sites move.
